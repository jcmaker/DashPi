# DashPi 이미지 전송과 네이티브 리포트 구현 계획

작성일: 2026-10-08

목표는 영상이 포함된 HTML 대신 대표 이미지 3장과 분석 JSON을 LCD QR로 보내고, 휴대폰에서 사진과 관찰 문장이 연동되는 리포트를 즉시 보여 주는 것이다. 새 앱을 먼저 배포하고 Pi 전송을 나중에 전환한다. 아래 체크리스트는 최초 구현 계획이며, 실제 검증 상태는 다음 기록을 기준으로 한다.

설계 원본은 `feat/native-report-screen` 작업 폴더의 `docs/superpowers/specs/2026-10-04-native-report-screen-design.md`이다. 아래 규격 요약과 결정 사항을 구현 기준으로 삼는다. 구현 시작 시 원본도 저장소의 지속적인 문서 경로에 함께 보존한다.

## 2026-10-08 구현·검증 기록

- 앱 JSON 검증, 사진·관찰 연동, 저장 목록, 오프라인 HTML 공유와 Pi 60,000 B 이하 전송·기존 기록 변환을 구현했다. 새 의존성은 없다.
- 교차 리뷰의 임시 파일 심볼릭 링크 덮어쓰기, 변환 중 삭제된 기록 복원, 목록에서 구 HTML/영상 전체 읽기를 수정하고 회귀 테스트를 통과했다.
- 최종 전체 Python 545개 통과(기존 FastAPI 경고 14개). 네이티브 Node 67개 통과, TypeScript 통과, 변경된 앱 코드 lint 통과. 웹 테스트 33개 통과·1개 건너뜀. Android Metro production export와 Expo prebuild 통과. Android 컴파일·서명은 릴리즈 워크플로에서 검증한다.
- 기존 Pi 기록 두 건의 변환 결과는 59,303 B/82블록/최소20.5초, 59,363 B/84블록/최소21초다. 현재 검증 규칙을 만족하지 않는 옛 분석 결과 한 건은 HTML 대체 전송 대상이다.
- 생성한 공유 HTML을 Chrome 모바일 390px 화면에서 확인했다. 세 JPEG가 디코딩되고 가로 넘침이 없다. 이는 네이티브 화면의 실기 확인을 대신하지 않는다.
- 사용자가 Android 휴대폰이 연결되지 않았다고 답했다. 앱 화면·글자 확대·공유 시트·구 HTML 재생의 실기 회귀, 실제 LCD→휴대폰 수신 시간, 다른 휴대폰의 오프라인 HTML 열기는 미검증이다.
- 앱 배포 후 Pi를 전환한다. 휴대폰 설치 여부는 확인할 수 없으므로 실제 수신 전 앱 1.2.0 설치가 필요하다. Pi 백업·배포 결과와 최종 전체 Python 결과는 릴리즈 기록에 남긴다.

## 확정된 범위와 결정

- LCD 전송: 이미지 3장과 JSON을 DPC1 파일 하나로 전송한다. DPQ1/DPC1, 512 B 블록, 현재 QR 크기와 250 ms 간격을 유지한다.
- 이미지: 가로 480px JPEG을 기본으로 하고 원래 종횡비를 유지한다. 480×270은 16:9 입력일 때의 크기다. 원본과 기존 대표 이미지 파일은 덮어쓰지 않는다.
- 2026-10-08 사용자 답변: 60 KB 이하를 우선한다. JPEG 품질을 먼저 낮추고 필요하면 해상도도 낮춘다. 실제 이미지 품질과 수신 시간을 검증한다.
- 2026-10-08 사용자 답변: 예전 기록도 기존 이미지로 새 전송 파일을 생성한다. 실패하면 기존 HTML 전송으로 전환되었음을 안내한다.
- 용량 판정은 UTF-8 JSON 원문 60,000 B 이하로 한다. 실제 QR 시간 계산은 압축과 컨테이너 헤더를 포함한 블록 수로 한다. 60 KB라는 표기만으로 30초 수신을 보장하지 않는다.
- 앱 화면: 큰 사진, 사고 전·순간·후 버튼, AI 요약, 시간별 관찰, 한계, 접힌 12개 항목 확인표, 긴급 번호, 접힌 증거 상세 순서다. 하단에 공유 또는 저장과 새로 받기를 둔다.
- 공유: 앱이 검증된 JSON에서 이미지 포함 HTML 하나를 만든다. 브라우저에서 오프라인으로 열리며 스크립트를 넣지 않는다.
- 저장: 앱 내부에 원본 수신 파일을 자동 보관하고 바로 표시한다. 외부 파일 저장이나 공유를 먼저 요구하지 않는다.
- 기존 HTML 리포트와 영상 생성, 웹 수신 흐름을 유지한다. 객체 추적과 사고 시점 탐색, Wi-Fi 전송, QR 속도 조정은 이번 작업에서 제외한다.
- 새 의존성을 추가하지 않는다. 이미지 처리는 설치된 OpenCV, 모바일 해시는 설치된 expo-crypto, 저장·공유는 기존 구현을 사용한다.

## 선행 코드와 작업 기준

계획 작성 당시 로컬 `main`은 `800ab30`이었으나, 구현 시작 때 원격 `main`의 `1e6cfc63d356dad8a33a7217a588594c181b51c1`을 기준으로 별도 작업 폴더를 만들었다. 이 기준에는 12개 항목 확인표와 늦게 시작한 QR 수신 수정이 이미 포함돼 있다. 기존 Mac/Pi의 미커밋 녹화 오버레이 수정은 보존한다.

- [ ] 구현 시작 시 원격 상태와 기준 커밋을 확인하고 선행 코드가 있는 기준에서 작업한다. 기존 기능을 다시 구현하지 않는다.
- [ ] 최종 통합 대상에 선행 커밋이 들어 있는지 확인한다. 설계 브랜치에 있다는 사실만으로 main에 구현되었다고 판단하지 않는다.
- [ ] 현재 main의 미커밋 `desktop.py`, `test_desktop.py` 수정은 보존한다. 별도 작업 폴더에서 구현한다.
- [ ] Expo API를 사용하는 코드 작성 전에 Expo 57 공식 문서를 읽는다. 현재 앱 구조에 새 라우터를 도입하는 작업은 추가하지 않는다.

## 전송 규격

Pi 내부 파일은 `report.transfer.json`, 전송 이름은 `dashpi-<incident_id 앞 8자>.json`, 미디어 타입은 `application/vnd.dashpi.report+json`이다.

필수 내용은 `format: dashpi.report`, `version: 1`, 사고 ID, 발생·생성 시각, 모델, 원본 클립 기준 사고 시각, 요약, 관찰 목록, 한계, 12개 항목 확인표, 경고, 이미지 3장, 원본 클립 SHA-256이다. 이미지에는 `role`, 원본 클립 기준 `timestamp`, `jpeg_base64`, 전송 JPEG의 `sha256`을 넣는다. 역할은 before, moment, after가 하나씩 있어야 한다.

화면의 상대 시각은 `timestamp - incident_timestamp`로 계산한다. 영상 시작·끝에 걸리면 전·후 이미지 시각이 ±2초보다 짧아질 수 있다. 가장 가까운 이미지에 관찰 문장을 배정하며 거리가 같으면 사고 순간 이미지, 그다음 앞선 이미지를 선택한다.

## 1 앱의 새 리포트 검증과 표시 분기

변경 대상: `receiver-native/src/preview-model.ts`, `preview-storage.ts`, `App.tsx`. 새 형식의 자료형과 검증은 `src/native-report.ts`에 둔다. 기존 `native-container.ts`, `unpack.ts`의 컨테이너 검증을 재사용한다.

- [ ] JSON 파싱과 필드 검증을 구현한다. 형식·버전, 필수 타입, 유효한 날짜, 유한한 비음수 시각, 이미지 역할과 개수를 검사한다.
- [ ] base64 길이를 디코딩 전에 확인하고 이미지마다 디코딩 후 200,000 B 이하, JPEG 시작 시그니처, SHA-256을 검사한다. native Image의 디코딩 실패도 이미지 손상으로 처리한다.
- [ ] 형식 오류면 리포트를 열 수 없다는 안내를 보여 주되 원본 JSON 보관·공유를 유지한다. 특정 이미지 오류면 그 자리만 이미지 손상으로 표시한다.
- [ ] 알려진 12개 항목만 표시하고 빠진 항목이나 알 수 없는 상태는 확인 불가로 처리한다. 속도·면허·음주 항목은 기존 분석 규칙대로 확인 불가로 유지한다.
- [ ] `PreviewModel`에 새 리포트 분기를 추가한다. `previewForFile`의 기존 HTML·영상 호출과 반환 동작을 유지하고 새 리포트의 이미지 해시는 비동기로 검사한다.
- [ ] `writePreview`는 새 리포트에 HTML·영상 임시 파일을 만들지 않는다. 새 분기를 추가하면서 기존 union을 소비하는 모든 호출부와 테스트를 수정한다.
- [ ] 파일을 바꾸거나 새로 받기를 누른 뒤 이전 검증 결과가 화면을 덮지 않도록 현재 수신 세대와 effect 취소 패턴을 유지한다.

검증: 정상 JSON, 형식·버전·필드 오류, 날짜·NaN 등 숫자 오류, 역할 중복·이미지 4장, 잘못된 base64·JPEG, 과대 이미지, 해시 불일치, 모르는 확인표 상태, 기존 HTML·영상 분기. 컨테이너 해시 오류는 기존처럼 저장 이전에 거부한다.

## 2 사진과 문장이 연동되는 앱 화면

변경 대상: `receiver-native/App.tsx`. 리포트 표시 컴포넌트는 `src/NativeReportView.tsx`에 두고 자료형·상대 시각·이미지 배정은 1단계의 모듈을 사용한다.

- [ ] 처음에는 사고 순간 이미지를 보여 준다. 전·순간·후 버튼에 실제 상대 시각을 표시한다.
- [ ] 사진 선택에 따라 해당 관찰 문장을 강조하고 문장을 누르면 연결된 사진을 선택한다. 관찰은 시각 순으로 표시한다.
- [ ] 설계의 화면 순서와 접힘 기본값을 구현한다. 긴급 번호는 일반 텍스트로만 표시한다.
- [ ] 확인표는 관찰됨 파랑, 관찰되지 않음 회색, 확인 불가 호박색으로 표시하고 법적 판단이 아니라는 설명을 둔다.
- [ ] 수신 파일 이름과 상세 해시는 증거 상세에 둔다. 하단 고정 버튼과 스크롤 본문이 겹치지 않도록 한다. 저장본 삭제는 증거 상세 안으로 이동한다.
- [ ] 버튼의 선택·접힘 상태, 이미지 설명, 읽을 수 있는 대비, 터치 영역과 글자 크기 확대를 확인한다. 이미지 손상은 색만으로 알리지 않는다.
- [ ] QR 카메라, 수신 진행률, 중단·새로 받기 동작은 기존 흐름을 사용한다.

검증: 상대 시각, 동률·경계 시각의 이미지 배정은 Node 단위 테스트로 확인한다. 실제 레이아웃, 사진 전환, 문장 강조, 긴 문장, 글자 확대, 작은 화면과 하단 버튼은 에뮬레이터와 휴대폰에서 확인한다. 새 UI 테스트 도구는 추가하지 않는다.

## 3 저장 목록과 HTML 공유

변경 대상: `saved-reports.ts`, `document-reports.ts`, `share-sheet.ts`, `App.tsx`. HTML 생성은 `src/report-html.ts`에 둔다. `share-report.ts`와 네이티브 공유 모듈의 캐시 이름·파일 접근·정리 규칙을 유지한다.

- [ ] 저장 목록을 읽을 때 새 JSON의 사고 시각, 요약 첫 줄, 검증된 순간 이미지로 행을 구성한다. 새 데이터베이스나 별도 인덱스를 추가하지 않는다.
- [ ] 새 기록은 사고 시각 내림차순으로 정렬한다. 구 HTML은 기존 파일 이름 표시와 열기를 유지하고, 시각을 알 수 없는 항목은 뒤에 안정적인 파일 이름 순으로 둔다.
- [ ] 읽기·검증 실패 항목도 열 수 없는 리포트로 남겨 삭제할 수 있게 한다. 목록 파일 하나가 손상돼도 전체 목록을 막지 않는다.
- [ ] 공유 시 새 리포트를 `dashpi-<id>.html`, `text/html`로 변환해 기존 `shareReport` 흐름에 전달한다. 원본 JSON은 그대로 보관한다.
- [ ] 공유 HTML에 세 이미지를 모두 넣고 모바일 화면과 같은 요약·관찰·한계·확인표·해시를 표시한다. 긴 문장은 모바일 브라우저에서 줄바꿈한다.
- [ ] 모든 텍스트를 HTML 이스케이프하고 외부 자원·스크립트·이벤트 속성을 만들지 않는다. 손상 이미지는 포함하지 않고 손상 안내를 넣는다.
- [ ] 형식 자체가 잘못된 JSON은 HTML로 변환하지 않고 원본 파일로 공유한다. 공유 취소·실패 뒤 저장본과 리포트 화면을 유지한다.

검증: 새 JSON·구 HTML·손상 파일이 섞인 목록, 날짜 정렬, 삭제, 재시작 후 다시 열기, HTML 이스케이프, 외부 연결 없는 HTML, 이미지 손상 안내, 공유 실패·취소 시 원본 보존. 다른 기기에서 공유 HTML을 오프라인으로 연다.

## 4 Pi 전송 JSON 생성과 기존 기록 변환

변경 대상: `reports.py`, `pipeline.py`, `models.py`, `storage.py`, 필요 시 `vision.py`와 `media.py`. 테스트는 기존 `test_reports.py`, `test_pipeline.py`, `test_models.py`, `test_incidents.py`, `test_vision.py`, `test_media.py`에 관련 사례를 추가한다.

- [ ] `IncidentMetadata`에 선택적인 전송 파일 artifact를 추가한다. `to_dict`와 저장소의 복원 루프를 함께 수정하고, 옛 metadata에 필드가 없어도 읽히게 한다.
- [ ] 새 분석에서는 기존 대표 JPEG 세 장을 읽어 전송용으로만 다시 인코딩한다. 영상, 원본 JPEG, 기존 report.json·report.html은 유지한다.
- [ ] 먼저 480px과 JPEG 품질 후보를 시도하고, 원문 JSON이 60,000 B를 넘으면 더 낮은 품질과 해상도를 제한된 순서로 시도한다. 무한 반복이나 원본 덮어쓰기를 하지 않는다.
- [ ] 사진 역할, 추출 시각, 재인코딩한 바이트의 해시를 JSON에 넣는다. 프레임 시각을 함께 전달할 필요가 있으면 `annotate_clip`의 pipeline 호출과 대체 추출 경로 및 테스트를 같이 수정한다.
- [ ] 새 기록에는 실제 선택한 프레임 시각을 보고서에 기록한다. 옛 JPEG에 추출 시각이 없으면 기존 추출 규칙과 영상 범위로 선택 지점을 재구성하고 warnings에 추정 시각임을 밝힌다. ±2초를 항상 고정값으로 표시하지 않는다.
- [ ] 분석의 관찰·요약·한계를 임의로 잘라 용량을 맞추지 않는다. 이미지 압축 후보로도 60 KB를 맞추지 못하면 변환 실패로 처리하고 기존 HTML 전송 안내를 사용한다.
- [ ] 전송 파일은 `atomic_write`로 기록하고 성공한 artifact만 metadata에 반영한다. 생성 실패가 기존 READY 리포트나 원본 증거를 무효화하지 않게 한다.
- [ ] 기존 기록 변환은 QR 준비의 작업 스레드에서 한 번 수행한다. 기존 report.json·JPEG의 경로와 저장된 해시를 확인한 뒤 읽고 AI 호출이나 영상 재분석을 하지 않는다.
- [ ] 옛 report.json에 확인표가 없다면 12개 항목을 확인 불가로 채운다. 관찰되지 않음이라는 결론을 만들어내지 않는다.

검증: 장면이 단순한 JPEG와 고주파·노이즈 이미지, 16:9 외 입력, 영상 처음·끝의 사건, 60 KB 경계, 텍스트만으로 용량을 넘는 사례, 이미지 해시, 원본 증거와 JPEG 불변, 재생성·재시작, 옛 metadata와 옛 기록, 손상 파일·경로·해시 오류, 변환 실패 뒤 기존 리포트 보존.

## 5 LCD 전송 전환과 웹 호환성

변경 대상: `desktop.py`, `test_desktop.py`. API와 웹은 기존 동작을 검증한다.

- [ ] `_prepare_optical`에서 새 artifact를 우선 읽고, 없으면 4단계의 기존 기록 변환을 시도한다.
- [ ] 기존 descriptor 기반 경로·파일 길이·해시 검증을 유지한다. 새 전송 파일의 유무만 확인하고 임의 경로를 여는 방식으로 바꾸지 않는다.
- [ ] 새 세션의 내부 파일은 report.transfer.json이지만 수신 이름과 미디어 타입은 전송 규격을 사용한다.
- [ ] 변환 실패 시 기존 report.html 세션을 만들고 LCD에 기존 영상 포함 전송이라 오래 걸릴 수 있다는 안내를 표시한다. HTML도 유효하지 않으면 오류를 표시한다.
- [ ] QR 크기·간격·블록 크기는 유지한다. JSON 파일 크기와 실제 컨테이너의 block_count로 예상 소요 시간을 계산하고 프레임 손실에 따른 추가 시간을 구분한다.
- [ ] `/api/incidents/{id}/report.html`, API의 report 광학 전송과 웹 수신은 기존 HTML을 유지한다. 모바일 LCD 전송 전환 때문에 웹 미리보기가 깨지지 않게 한다.

검증: 새 JSON 세션, 옛 기록 최초 변환과 다음 재사용, 실패 시 HTML 안내, 잘못된 path·해시, UI 응답성, 준비 중 화면 이탈과 중복 탭, 기존 API·웹 HTML 수신.

## 6 전체 검증과 배포

- [ ] 테스트 JPEG을 가진 전송 JSON을 Python 생성기에서 만들고 DPC1·DPQ1 프레임 fixture를 만든다. `tests/fixtures/optical-report-v1.json`처럼 기존 optical fixture와 분리한다.
- [ ] 앱 테스트에서 같은 Python 프레임을 기존 FrameCollector와 native 컨테이너 로직으로 복원하고 저장·JSON 검증·이미지 해시·화면 모델·HTML 공유까지 확인한다. 프레임 누락·중복·순서 뒤섞임과 늦게 수신을 시작하는 사례를 포함한다.
- [ ] Python 관련 테스트, 네이티브 Node 테스트, TypeScript 검사와 lint를 실행한다. 현재 package.json에 lint 명령이 없으므로 구현 시 기존 CI 도구를 확인해 실행 가능한 검사 명령과 결과를 기록한다. 문서의 명령만으로 lint 통과를 주장하지 않는다.
- [ ] 모바일 기기에서 구 HTML 수신·저장·재생·공유 회귀를 확인한다. 이번 변경으로 수정한 공유 흐름은 취소·실패·재시도를 함께 확인한다.
- [ ] 새 앱을 먼저 배포해 구 Pi의 HTML을 정상 표시하는지 확인한다. Pi 전송 변경은 새 앱 설치 확인 뒤 배포한다.
- [ ] 실제 Pi LCD와 휴대폰으로 주간·야간·복잡한 장면을 수신한다. QR 표시부터 검증된 리포트 표시까지의 시간, 원문·컨테이너 용량, 블록 수, 재전송 영향을 기록한다.
- [ ] 30초 안팎 수신과 사고 장면 식별 가능한 사진 품질을 목표로 삼는다. 해상도 축소가 필요한 사례는 시안과 실기 결과로 판단하며 번호판 판독을 보장하지 않는다.
- [ ] 공유 HTML을 다른 휴대폰 브라우저에서 오프라인으로 열고, 저장 목록 재열기와 예전 기록 변환·HTML 대체 안내를 확인한다.

앱 자동 테스트 통과, Pi JSON 생성 완료, 실제 LCD 수신 성공, 배포 완료는 각각 나눠 보고한다. Pi가 꺼져 있어도 자동 테스트와 앱 화면 구현은 진행할 수 있지만 실제 전송 시간 완료 조건은 실기 측정으로만 충족한다.

## 구현 순서와 완료 기준

선행 코드 확인 → 앱 형식 검증 → 앱 화면 → 저장·공유 → Pi 파일 생성·기존 기록 변환 → LCD 전환 → 전체 자동 검증 → 앱 선배포 → Pi 배포·실기 검증 순서다. 각 단계는 관련 테스트와 함께 완결되는 변경 단위로 만든다.

완료 시 새 기록과 변환 가능한 예전 기록이 60 KB 이하 JSON으로 전송되고, 휴대폰이 즉시 사진·문장 연동 리포트를 표시하며, 저장 목록과 공유 HTML에서 같은 내용을 확인할 수 있어야 한다. 변환 불가 기록의 기존 HTML 안내와 기존 HTML 호환성도 완료 조건에 포함한다. 실제 수신 시간과 이미지 품질은 실기 결과를 함께 제시한다.
