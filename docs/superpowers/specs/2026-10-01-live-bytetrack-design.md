# Pi 실시간 ByteTrack 프리뷰 설계

상태: 사용자 검토 대기. 구현 착수 전에 이 설계를 확인한다.

## 목표

주행·주차 녹화 중 Pi LCD의 기존 카메라 프리뷰에 도로 객체의 컬러 사각형, 클래스, 추적 ID를 실시간 표시한다. 녹화 원본에는 박스를 넣지 않는다. 인터넷 없이 감지·추적한다.

## 확인한 장치와 코드

- SSH: `ssh wonmaker`, 호스트 `WONMAKER-RPI`.
- Raspberry Pi 5 Model B, RAM 4GB, Debian 13 trixie, IMX708 카메라.
- 실행 중 앱: `/home/wonmaker/DashPi-native/.venv/bin/python -m dashpi.desktop`.
- `/home/wonmaker/DashPi`는 별도 구버전 체크아웃이다. 배포 대상은 실행 중 앱의 `DashPi-native`이다.
- native 가상환경에는 Picamera2, PySide6, OpenCV가 있다. supervision, ultralytics, scipy는 없다. ONNX 파일은 해당 체크아웃의 깊이 3까지 검색했을 때 발견되지 않았다.
- 설치된 `QGlSide6Picamera2.set_overlay()`는 RGBA 배열을 받는다. Qt 메인 스레드에서 호출해야 한다.
- `PiCameraRecorder`가 카메라를 한 번 열고 프리뷰와 분할 MP4를 함께 제공한다.
- `vision.YoloDetector`는 OpenCV DNN 기반 YOLOv8 COCO ONNX 감지기다. 기존 `assign_track_ids`는 IoU 매칭이며 ByteTrack이 아니다.
- 로컬 작업 브랜치: 최신 `origin/dev`에서 만든 `feat/live-bytetrack`.

## 접근 비교

1. **추천: 기존 OpenCV 감지기 + supervision ByteTrack + Picamera2 오버레이.** 기존 카메라와 감지기를 재사용한다. 새 의존성은 실제 ByteTrack 구현에 필요한 선택 의존성으로 한정한다.
2. Ultralytics 전체 스택 사용: 감지·추적 연결은 편하지만 Pi에 PyTorch 등을 추가하게 된다.
3. ByteTrack 직접 구현: 의존성은 줄지만 Kalman filter와 데이터 연관 알고리즘을 직접 유지해야 하므로 채택하지 않는다.

## 데이터 흐름과 화면

`Picamera2 단일 카메라 → 저해상도 lores 프레임 → YOLOv8n ONNX → ByteTrack → RGBA 박스 → 기존 Qt 프리뷰`

- 메인 스트림과 인코더는 기존 녹화 설정을 유지한다.
- 감지용 lores 스트림은 640×360 YUV420으로 시작하고, OpenCV에서 BGR로 변환한다. 실제 장치의 스트림 제약에 맞춰 구성 가능 여부를 확인한다.
- 작업자 하나가 프레임을 읽고 추론한다. 무제한 큐를 만들지 않는다. 처리 중 들어온 과거 프레임은 쌓지 않고 다음 추론에 최신 프레임을 사용한다.
- 목표 추론 빈도는 최대 10Hz이며 실제 Pi FPS를 측정한다. 화면 프리뷰 FPS와 추론 FPS를 따로 기록한다. 10Hz를 성능 보장으로 표현하지 않는다.
- 프레임 좌표와 프리뷰 표시 비율을 일치시키고, 투명 RGBA 오버레이를 Qt 메인 스레드에서 적용한다. 영상이 차지하는 기존 영역과 버튼 배치를 재사용한다.
- 대상은 person, bicycle, car, motorcycle, bus, truck이다. 같은 활성 track ID에는 결정적 색상 계산으로 같은 색상을 사용한다.
- 추적이 끊겨 새 ID가 생성되면 색상도 바뀔 수 있다. 영구적인 사람·차량 식별 기능은 아니다.
- 추론 결과가 1초 이상 오래되면 박스를 지운다. 녹화 세션이 바뀌면 tracker와 결과를 초기화한다.

## 감지기·추적기 연결

- 실제 ByteTrack 구현은 supervision의 공개 `ByteTrack` API를 사용한다. Pi Python·NumPy와 맞는 버전을 설치 검증 후 고정한다.
- 기존 detector의 기본 confidence 0.45와 저장 영상 동작을 유지한다. live 경로만 confidence 0.10으로 감지해 ByteTrack의 저신뢰도 매칭에 제공한다.
- 높은 신뢰도 활성 임계값은 0.45, 저신뢰도 감지 하한은 0.10으로 시작한다. 실제 노이즈와 속도에 맞춰 조정할 수 있도록 설정 값을 둔다.
- 클래스가 다른 객체의 ID가 섞이지 않도록 도로 객체 클래스별 tracker를 사용하고, 화면에 표시할 ID는 세션 안에서 유일하게 만든다.
- ONNX 감지 모델은 YOLOv8n COCO, 입력 640×640, 기존 감지기가 지원하는 출력 형식으로 준비한다. 모델 경로는 명시적으로 지정한다. 앱 실행 중 모델을 다운로드하지 않는다.
- 모델 누락·잘못된 출력·추론 오류는 추적 표시만 중단한다. 기존 상태 표시 영역에 추적 오류를 알리고 녹화·프리뷰는 계속한다.

## 수명주기와 증거 보호

- 카메라 준비 후 녹화가 성공하면 추적 작업자를 시작한다.
- 종료·시작 실패·카메라 해제에서는 작업자 종료, 결과 무효화, 오버레이 제거를 처리한다. 이전 세션의 작업자가 새 카메라를 사용하지 못하게 한다.
- 요청에서 읽은 배열은 즉시 복사하고 Picamera2 요청을 해제한다. 추론이 카메라 버퍼를 점유하지 않게 한다.
- 박스는 프리뷰 위에서만 합성한다. 원본 MP4, 세그먼트 시간, 사고 전후 구간, SHA-256 및 분석 재시도 동작은 기존 경로를 따른다.
- 최초 검증은 별도 data root의 짧은 녹화로 수행한다. 기존 raw 영상·사고 기록·API 키 파일은 보존한다.
- 실행 중 앱의 데이터 루트를 확인하고 정상 종료한 뒤 검증 앱을 띄운다. 카메라를 두 프로세스에서 동시에 열지 않는다.

## SDD 실행 순서

1. **추적 엔진:** 실제 ByteTrack 연결, detector 저신뢰도 입력, ID별 색상, 선택 의존성과 모델 설치 안내. 이동·저신뢰도 매칭·클래스 분리·빈 감지에 대한 작은 실행 가능한 테스트를 남긴다.
2. **카메라·Qt 통합:** lores 캡처, 단일 작업자, 메인 스레드 오버레이, 오래된 결과 제거와 세션 종료. fake camera 테스트로 단일 카메라 소유·종료·추론 실패 시 녹화 유지를 확인한다.
3. **Pi 배포·실측:** native 설치 경로를 확인하고 변경 코드와 모델을 배포한다. 박스 좌표·ID 연속성·종료 후 재시작·MP4 재생을 확인하고 추론 FPS, CPU, RAM, 온도를 기록한다.

각 코드 작업은 새 구현 에이전트가 맡고, 다른 에이전트가 설계 준수와 코드 품질을 리뷰한다. 전체 변경도 마지막에 리뷰한다. 실기 결과와 자동 테스트 결과를 구분해서 보고한다.

## 수락 조건

- 촬영·녹화 중 기존 Pi 화면에 객체 박스와 추적 ID가 반복 갱신된다.
- 같은 활성 ID는 같은 색상을 유지하고 화면 비율이 바뀌어도 박스 위치가 맞는다.
- 추론이 녹화 프레임 공급을 막지 않고 종료 후 카메라를 다시 열 수 있다.
- 감지 실패 시 원본 녹화와 기본 프리뷰가 계속된다.
- 검증 MP4를 ffprobe로 확인하고 실제 측정한 FPS·자원 사용량을 문서에 남긴다.
- GPU·AI 가속기, 새 화면 레이아웃, 원본 박스 저장은 이번 범위에 포함하지 않는다.
