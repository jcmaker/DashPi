# DashPi 네이티브 리포트 화면과 이미지 전송 설계

**작성일:** 2026-10-04
**상태:** 2026-10-08 구현 승인
**범위:** Pi 광학 전송 내용, 모바일 앱 리포트 화면, 저장 목록, 공유
**대체:** `2026-10-02-evidence-first-mobile-report-design.md`의 §3(HTML 전송)과 §6(모바일 레이아웃). 분석·12대 중과실 확인표 규칙(§4, §5)은 그대로 유지한다.

## 1. 배경

- 현재 Pi는 영상을 base64로 넣은 HTML(약 1.7 MB)을 QR로 보낸다. 512 B 블록 2512개를 250 ms 간격으로 보내므로, 손실이 없어도 약 10.5분이 걸린다.
- 측정 결과 1.7 MB 중 영상이 87%이고, 텍스트 전체는 압축 후 약 2 KB다. HTML을 다른 문서 형식으로 바꾸는 것만으로는 빨라지지 않는다.
- 레퍼런스(차량 관제 이벤트 화면, 블랙박스 뷰어)는 짧은 증거와 사건 순간 마커를 맨 위에 둔다. 사건 종류에 따라 사진 한 장으로 대신하기도 한다.
- 시안 비교에서 사용자는 "A: 증거 먼저 한 장 스크롤"에 "B: 사진·문장 동기화"를 더한 안을 골랐다.

## 2. 결정 사항

| 항목 | 결정 |
|---|---|
| 전송 내용 | 영상 대신 대표 이미지 3장(사고 전, 순간, 후)과 구조화된 JSON |
| 이미지 | 가로 480px JPEG(480×270), 장당 약 11 KB |
| 화면 | 앱이 JSON을 읽어 네이티브로 그림(A+B) |
| 공유 | 앱이 받은 JSON으로 HTML 파일 하나를 만들어 공유 |
| 저장 목록 | 파일 이름 대신 사고 시각과 사고 순간 썸네일로 표시 |
| 광학 규격 | DPQ1 프레임과 DPC1 컨테이너는 바꾸지 않음 |

예상 전송량은 약 50 KB(이미지 base64 포함)다. 블록 약 100개, 손실이 없으면 약 25초다.

2026-10-08 사용자 결정: 60 KB 이하를 우선하고 JPEG 품질과 필요 시 해상도를 낮춘다. 예전 기록도 기존 대표 이미지에서 새 전송 파일을 생성하며, 실패하면 기존 HTML 전송임을 안내한다. 실제 이미지 품질과 수신 시간은 실기에서 확인한다. 영상 경계에서 이미지의 상대 시각은 ±2초와 다를 수 있으므로 실제 추출 시각을 표시한다.

## 3. 전송 형식

DPC1 컨테이너의 파일 하나로 보낸다.

- 이름: `dashpi-<incident_id 앞 8자>.json`
- 미디어 타입: `application/vnd.dashpi.report+json`
- 압축: 기존 DPC1 deflate 사용(텍스트만 줄어들고 JPEG은 거의 그대로)

```json
{
  "format": "dashpi.report",
  "version": 1,
  "incident_id": "68fe0b3d0ddf4d36ab2160e98322c565",
  "triggered_at": "2026-10-04T04:00:02.082710+00:00",
  "generated_at": "2026-10-04T04:00:06.529004+00:00",
  "model": "x-ai/grok-4.7 + x-ai/grok-4.20",
  "incident_timestamp": 3.433,
  "summary": "…",
  "observations": [{ "timestamp": 0.68, "description": "…" }],
  "limitations": ["…"],
  "major_negligence_review": {
    "signal": { "status": "observed", "evidence": "…", "timestamp": 5.2 }
  },
  "warnings": ["…"],
  "keyframes": [
    { "role": "before", "timestamp": 1.433, "jpeg_base64": "…", "sha256": "…" },
    { "role": "moment", "timestamp": 3.433, "jpeg_base64": "…", "sha256": "…" },
    { "role": "after",  "timestamp": 5.433, "jpeg_base64": "…", "sha256": "…" }
  ],
  "digests": { "clip.mp4": "…" }
}
```

- 모든 `timestamp`는 기존과 같이 증거 클립 시작 기준 초다. 화면에서 사고 순간을 0초로 바꾼다.
- `sha256`은 전송된 JPEG 바이트의 해시다. 원본 증거와 구분하기 위해 `digests`에는 원본 클립 해시를 그대로 둔다.
- base64를 쓰면 이미지가 33% 커지지만(약 11 KB 증가, 약 5초), 별도 바이너리 묶음 형식을 만들지 않아도 된다. 전송 시간이 문제가 되면 그때 바꾼다.

## 4. Pi 변경

1. 기존 대표 이미지(`keyframes/before|moment|after.jpg`, 사고 순간 ±2초)를 가로 480px JPEG으로 다시 저장해 전송용 JSON을 만든다. 파일: `report.transfer.json`.
2. LCD의 QR 전송은 `report.html` 대신 `report.transfer.json`을 보낸다.
3. `report.html`과 `annotated.mp4`는 Pi와 웹 수신기용으로 계속 만든다. 이번 범위에서 영상 생성을 없애지 않는다.
4. 녹화 영상 분석에서 객체 인식기가 빠져 박스가 없는 문제는 이번 범위가 아니다(실시간 추적 작업과 함께 다룬다).

## 5. 앱 화면 (A+B)

수신과 SHA-256 검증이 끝나면 저장이나 다운로드 단계 없이 바로 표시한다. 위에서 아래로:

1. **헤더:** 사고 시각(현지 시간대, `2026-10-04 13:00:02 KST`), `무결성 검증 완료` 표시
2. **장면 영역:** 큰 사진 1장, 그 아래 `사고 전 · 사고 순간 · 사고 후` 전환 버튼(각 버튼에 -2.0초 / 0.0초 / +2.0초). 처음에는 사고 순간을 보여 준다.
3. **AI 요약**
4. **시간별 관찰:** `-2.7초`처럼 사고 기준 상대 시각으로 표시한다. 각 문장은 시각이 가장 가까운 대표 이미지에 속한다. 선택한 이미지에 속한 문장은 진하게, 나머지는 흐리게 보인다. 문장을 누르면 그 문장이 속한 이미지로 바뀐다.
5. **영상으로 확인할 수 없는 내용:** `limitations`와 `warnings`
6. **12대 중과실 관련 영상 확인**(기본 접힘): 제목 아래에 "법적 판정이 아니라 관련 장면이 보였는지만 정리했습니다" 문구. 상태 칩은 `관찰됨`(파랑), `관찰되지 않음`(회색), `확인 불가`(호박색). 빨강·초록처럼 판정으로 읽히는 색은 쓰지 않는다. 근거와 시각이 있으면 칩 아래에 표시한다.
7. **긴급 번호:** `119 구급·소방`, `112 경찰`. 일반 텍스트로만 쓰고 전화 걸기 동작은 없다.
8. **증거 상세**(기본 접힘): 사고 ID, 생성 시각, 모델, 원본 클립과 이미지 3장의 SHA-256
9. **하단 고정 바:** `공유 또는 저장`, `새로 받기`. `저장본 삭제`는 증거 상세 맨 아래에 둔다.

QR 촬영 화면은 바꾸지 않는다.

## 6. 공유

`공유 또는 저장`을 누르면 앱이 JSON으로 HTML 파일 하나(`dashpi-<id>.html`)를 만들어 기존 공유 시트로 넘긴다.

- 내용과 순서는 §5와 같다. 이미지는 data URI로 넣고 스크립트는 넣지 않는다. 장면 전환은 HTML에서 세 장을 나란히 보여 주는 것으로 대신한다.
- 모든 텍스트는 HTML 이스케이프한다.

## 7. 저장 목록

- 새 형식 리포트는 행마다 사고 순간 썸네일, 사고 시각, 요약 첫 줄을 보여 준다. 최신순으로 정렬한다.
- 예전 HTML 리포트는 지금처럼 파일 이름으로 보이고, 열면 기존 WebView로 표시한다.
- 목록을 만들 때 JSON을 읽는다(리포트당 약 50 KB). 읽을 수 없는 파일은 목록에서 빼지 않고 "열 수 없는 리포트"로 표시해 삭제할 수 있게 한다.

## 8. 호환성

- `previewForFile`이 미디어 타입으로 갈라진다: `text/html`은 기존 WebView, `application/vnd.dashpi.report+json`은 새 화면.
- 새 Pi와 구 앱(1.1.3 이하): 구 앱은 이 미디어 타입을 미리 볼 수 없다는 메시지를 띄우고 저장·공유만 가능하다. 앱을 먼저 배포하고 Pi를 나중에 업데이트한다.
- 구 Pi와 새 앱: HTML 리포트가 오면 기존대로 표시한다.

## 9. 신뢰 경계와 검증

QR로 받은 JSON은 SHA-256이 맞아도 Pi가 만든 내용이므로 앱에서 형식을 검증한다.

- `format`/`version` 확인, 필수 필드와 타입 확인. 맞지 않으면 "리포트를 열 수 없습니다"를 표시하고 원본은 저장·공유할 수 있게 둔다.
- `keyframes`는 정확히 3개이고 role은 before, moment, after. 각 이미지는 JPEG 시그니처(`FF D8`)로 시작하고 디코딩 후 200 KB 이하. `sha256`이 맞지 않으면 그 이미지 자리에 "이미지 손상"을 표시한다.
- 텍스트는 React Native `Text`로만 그린다. HTML로 해석하지 않는다.
- 확인표 키와 상태는 알려진 값만 표시하고, 모르는 값은 `확인 불가`로 보여 준다.

## 10. 테스트

자동 테스트:

- Pi: 전송 JSON에 필수 필드와 이미지 3장이 있고, 이미지가 가로 480px이며, 전체 크기가 60 KB 이하인지 확인
- Pi: LCD QR 세션이 `report.transfer.json`과 새 미디어 타입을 쓰는지 확인
- 앱: JSON 검증(정상, 필드 누락, 이미지 4장, JPEG 아님, 해시 불일치)
- 앱: 상대 시각 변환과 "가장 가까운 대표 이미지" 배정
- 앱: 공유용 HTML이 텍스트를 이스케이프하고 `<script>`가 없는지 확인
- 앱: `previewForFile`이 미디어 타입별로 올바른 화면을 고르는지 확인
- 실제 리포트로 Pi 프레임 생성 → 앱 수신 로직까지 끝까지 통과하는지 확인(기존 e2e 방식)

실기 테스트(Pi 전원을 켠 뒤): Pi LCD → 휴대폰 수신 시간 측정, 화면 확인, 공유 파일을 다른 휴대폰에서 열기.

## 11. 하지 않는 것

- 텍스트 먼저 받고 이미지는 나중에 받는 2단계 전송: 전체가 약 25초라 지금은 필요 없다. 느리게 느껴지면 다시 검토한다.
- QR 크기·간격 변경, Wi‑Fi 전송: 이미지 전송으로 충분히 빨라지는지 실기에서 확인한 뒤 판단한다.
- 객체 박스, 실시간 추적, 녹화 영상의 사고 시점 AI 탐색(별도 작업으로 보류 중).

## 12. 완료 조건

- Pi가 약 50 KB 전송 JSON을 만들고 LCD QR로 보낸다.
- 휴대폰이 30초 안팎에 받고 바로 A+B 화면을 보여 준다.
- 사진 전환과 문장 강조가 연동된다.
- 공유한 HTML 파일이 다른 기기 브라우저에서 같은 내용으로 열린다.
- 저장 목록에 사고 시각과 썸네일이 보이고, 예전 HTML 리포트도 계속 열린다.
